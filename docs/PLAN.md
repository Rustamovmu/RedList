# WildAtlas — product and technical specification (v3)

Working name: **Wildward** (renamed from WildAtlas; check domain and trademark availability before launch). This document is the specification. How the coding agent (Claude Code) should work is in `AGENTS.md`, which `CLAUDE.md` imports. The prompts to run one milestone at a time are in `docs/CLAUDE_TASKS.md`.

---

## 1. Product

**Promise:** Understand a species, see where it lives, and find a credible way to help.

**Audience:** The main audience is curious learners and students. Conservation supporters come second. Researchers are not a target for R1, so the site must not present itself as a research-grade biodiversity database.

**Core journey:** Discover → Understand → Explore place → Compare → Act. All of it works without an account.

**Coverage:** The catalogue is extensible. It can hold mammals, birds, reptiles, amphibians, fish, insects, arachnids, molluscs, crustaceans, corals and other invertebrates. For each species it records status, dated population estimates, geography, habitats, diet, climate, threats and conservation actions. We do not promise complete coverage of all life.

**Initial catalogue:** Start with 20–30 reviewed profiles and grow toward 100 once editing is sustainable. These counts are targets. They never justify inventing a fact, a source or an image.

## 3. Technical decisions

### Stack
| Concern | Decision |
|---|---|
| Runtime | Node.js current Active LTS, pinned in `.nvmrc` and `engines` |
| Repo | **Two repositories:** `RedList-backent` (API, database, docs) and `RedList-frontend` (web). Both use npm. (Changed from a Yarn monorepo; see DECISIONS D-002.) |
| Web | Next.js App Router, TypeScript strict, Tailwind CSS |
| API | NestJS with REST under `/api/v1` and OpenAPI generated by `@nestjs/swagger` |
| Contracts | The backend exports `openapi.json` (`npm run openapi:export`). The frontend generates `src/contracts/api.d.ts` from it (`npm run contracts:generate`). API types are never written by hand. |
| DB | PostgreSQL with PostGIS |
| ORM | **Drizzle ORM** with node-postgres (see DECISIONS D-001). Geometry columns are PostGIS `geometry(MultiPolygon,4326)` custom types. Spatial reads and writes use parameterized `sql` templates inside `GeoRepository`. Migrations are plain SQL in `drizzle/`; CHECK constraints and triggers are hand-written in custom migrations. |
| Validation | `zod` for editorial JSONB and import files. `class-validator` DTOs at the API boundary. |
| Map | MapLibre GL JS. The R1 basemap is the Natural Earth country and ocean polygons served from our own API, so no tile provider or API key is needed. A self-hosted Protomaps vector basemap is an optional later upgrade. |
| Boundaries | Natural Earth (public domain) for countries. Marine Regions for oceans and seas, after checking its license and attribution requirements. |
| Search | PostgreSQL full-text search over names. Add `pg_trgm` only when a failing test shows it is needed. |
| Storage | A `StorageAdapter` interface with a local-disk implementation for development and an S3-compatible one for production. The DB stores only metadata. |
| Images | Validate and re-encode on upload, strip EXIF/XMP, and generate responsive WebP variants. Serve them through `next/image` with a custom loader. |
| Tests | Jest + ts-jest (Nest needs decorator metadata) and supertest. Integration tests run against **real PostGIS** in a dedicated test database. Playwright for end-to-end. |

**Not in R1:** Redis, Elasticsearch, Kubernetes, vector DB, message broker, background worker or microservices. Small imports run as CLI commands.

**Why keep a separate NestJS API?** Future clients such as a mobile app or PWA, and a clean module boundary. If the solo maintenance cost proves too high, the documented fallback is to move the API modules into Next.js route handlers with the same DTOs. Record that decision in `DECISIONS.md` if it is taken.

### Layout
```
RedList-backent/              (API + database + project docs)
  src/                        NestJS modules: health (now); catalogue, geography, editorial,
                              identity, media, support-directory (added per milestone)
  src/db/schema.ts            Drizzle schema
  drizzle/                    SQL migrations (generated + hand-written integrity rules)
  src/cli/                    migrate, seed-regions, export-openapi (later: import, admin, links)
  data/natural-earth/         public-domain boundary data
  test/                       integration tests against PostGIS
  docs/                       PLAN, ARCHITECTURE, DECISIONS, DATABASE, DATA_SOURCES, BACKLOG, COMPLETED_TASKS, CLAUDE_TASKS
  docker-compose.yml          local PostGIS
RedList-frontend/             (Next.js public site + /admin)
  src/app, src/components, src/lib
  src/contracts/api.d.ts      generated from ../RedList-backent/openapi.json
```

### Runtime wiring
- Browser calls go to same-origin `/api`. Next.js server components use `API_INTERNAL_URL`. No hostnames are hardcoded.
- **Caching:** Next.js fetches published data with cache tags (`species:<slug>`, `catalogue`, `region:<slug>`). After a successful publish, rollback or archive, the API calls `POST /api/revalidate` on the web app with a shared secret, naming the affected tags. Because of this, a published change shows up everywhere at once with no time-based staleness window.
- Health: `/api/v1/health/live` and `/api/v1/health/ready` (the second checks the DB and PostGIS).
- Logging: structured JSON logs carrying a request ID. Passwords, tokens, cookies, emails and raw coordinates of sensitive species are redacted.

## 4. Public experience

### Style
The look is a calm nature-editorial style: warm off-white background, deep forest-green navigation, readable type and large licensed photographs. Conservation-status colours are never the only signal. Each one carries a text label and meets WCAG contrast. Avoid 3D globes, autoplay video, live counters and walls of identical cards. Respect `prefers-reduced-motion`.

**Accessibility target: WCAG 2.2 AA.** Everything must be keyboard-operable, with visible focus, skip link, semantic landmarks and correct heading order. The map always has an equivalent accessible list.

**Navigation:** Explore · Map · Compare · About. The support directory is linked from the footer and shown in species context.

### Pages

**Home `/`.** Shows a hero photograph with credit, the promise and a prominent search box. Visitors can browse by animal group and by environment. A curated row of threatened species and an entry point for countries and oceans follow, plus a three-line explanation of how we source facts. Statistics are database-derived and labelled "in this catalogue". They never claim to be global totals.

**Explore `/species`.**
- Search covers common and scientific names, including synonyms.
- Filters: animal group, environment, IUCN category, country or ocean, habitat, population trend. Group and environment are independent axes, so a whale is both a mammal and marine.
- Filters, sort and page are all held in the URL. Back and forward work, and links are shareable.
- On mobile the filters open in a drawer. Applied filters show as chips with a reset button. The page has empty and error states.
- Each card shows the photo, common and scientific name, group, status badge with assessment year, and one context line.
- Sort options are name, status severity, and recently reviewed. **No sorting by population size**, because the units are not comparable.

**Profile `/species/[slug]`.** The profile answers eight questions in this order:
1. **What is it?** Names, photo with credit, classification, overview.
2. **How threatened is it?** Category, scope (global or regional), assessment date, trend.
3. **How many remain?** Each estimate shows value or range, unit/basis (mature individuals, pairs, all individuals), wild or captive, scope, reference year, uncertainty and citation. Otherwise it shows **"Unknown"** with a one-line explanation.
4. **Where does it live?** Map, list of countries and oceans with presence, origin and season, habitats, climate.
5. **What does it eat?** Diet, with life-stage or seasonal context where it is known.
6. **Why is it threatened?** Specific threats and sourced conservation actions.
7. **How can I help?** Reviewed external links. Each states the receiving organization and the destination domain.
8. **How do we know?** Sources, photo licences, source dates, editorial review date and reviewer role.

Key facts appear first, with detail in expandable sections. Citations are never gated. The page also has an "Add to compare" control, related species chosen by shared group, region or threat, and a sticky in-page navigation on mobile.

**Map `/map`.** A map and results list kept in sync. Filters by viewport, group and status. Includes a legend, and every data layer is labelled with its kind ("Country-level presence" vs "Published range map"). When only countries are known, the map shades whole countries and says so. A species range is never invented. If tiles fail, the list still works and a notice explains the failure. The page never asks for geolocation on load. "Near me" is an explicit button that only filters by country.

**Regions `/regions/[slug]`.** Countries, seas and oceans each get a page with region-aware filters. It shows native, introduced and seasonal presence when the source distinguishes them. Species of the high seas belong to ocean regions, never to an invented country.

**Compare `/compare?species=a,b,c`.** Compares at most 3 species, and the selection is kept in the URL. Rows: status with date and scope, population with basis, group, habitats, diet, geography, threats. "Unknown" and "Not directly comparable" are shown explicitly. There is no overall score, no winner, and no bar chart mixing different units. On mobile it uses a stacked layout.

**Other pages.** `/about`, `/methodology`, `/sources`, `/support`, `/privacy`, `/terms`, `/admin`. Real operator details must be added before launch, with no invented affiliations or certifications. No empty articles section.

**SEO.** Server-rendered profiles, per-page metadata, canonical URLs, `sitemap.xml` (published content only), `robots.txt`, Open Graph images from licensed media, and schema.org structured data where it is valid.

## 5. Scientific data rules

1. **Population** is never a single number on the species row. Every estimate carries geography, date, basis, wild/captive context, source and uncertainty. Mature individuals, breeding pairs and total individuals are different quantities. Population is never inferred from sightings, never interpolated into a countdown, overlapping populations are never summed, and missing is never zero.
2. **Status codes:** EX, EW, CR, EN, VU, NT, LC, DD, NE, each with global or regional scope. DD and NE are not "low risk", and the UI never groups them with LC.
3. **Trend** is stored as the source reported it. No improvement is inferred from two estimates that used different methods.
4. **Climate** describes typical conditions, not weather. Numeric ranges need units, region or season context and a source. Unknown ranges are left absent.
5. **Names:** common names are language-tagged and identifiers are stable (scientific name plus provider IDs such as the GBIF taxon key or IUCN taxon ID). Taxa are never merged by common name. Species vs subspecies is supported.
6. **Sensitive species:** `species.location_sensitivity` is one of `none | generalize_country | hide_regions`. Public geometry for sensitive species is generalized before storage. Only approved public geometry is stored in R1. Raw coordinates are never logged, cached, exported or left in image metadata.
7. **Three dates kept separate:** source publication date, import date, editorial review date. All three are stored and shown.

## 6. Data model (R1)

UUID primary keys. `timestamptz` for instants, `date` for scientific dates. Explicit foreign keys, with `RESTRICT` wherever history matters. Before the first migration, record any adjustments in `docs/DATABASE.md` and draw the ER diagram in Mermaid.

### Identity (outside revisions, so change is rare and audited)
| Table | Fields |
|---|---|
| species | id, slug (unique), accepted_scientific_name, rank (`species`/`subspecies`), parent_species_id, location_sensitivity, published_revision_id, archived_at |
| species_identifiers | species_id, provider, external_id, source_url. Unique (provider, external_id). |

### Revisioned content (everything public about a species)
| Table | Fields |
|---|---|
| species_revisions | id, species_id, version (unique per species), state, schema_version, **display_group**, editorial JSONB, author_id, reviewer_id, submitted_at, reviewed_at, published_at, review_notes, base_revision_id. Immutable once submitted. |
| species_names | revision_id, language, name, name_type (`common`/`synonym`), preferred |
| species_environments | revision_id, environment (enum: `terrestrial`, `freshwater`, `marine`, `brackish`, `subterranean`, `aerial`). Relational because it is a primary filter. |
| assessments | revision_id, provider_assessment_id, source_id, scope, region_id, category, trend, assessed_on, published_on, criteria |
| population_estimates | revision_id, assessment_id (nullable, composite FK on the same revision), source_id, scope, region_id, context (`wild`/`captive`), basis (`mature_individuals`/`breeding_pairs`/`individuals`/`other`), form (`exact`/`range`/`at_least`/`at_most`/`qualitative`/`unknown`), point/min/max (bigint), qualitative_text, reference_start/end, method, uncertainty_note |
| species_regions | revision_id, region_id, presence, origin, seasonality, source_id |
| species_ranges | revision_id, source_id, geom (MultiPolygon 4326), seasonality, presence, dataset_version, generalization_note |
| species_habitats | revision_id, habitat_id, suitability, seasonality, source_id |
| species_threats | revision_id, threat_id, severity, timing, source_id |
| revision_citations | revision_id, section_key (validated enum), source_id, locator, note |
| revision_media | revision_id, media_id, position, role, alt_text, caption, **credit_snapshot, license_snapshot** |
| revision_support_links | revision_id, support_link_id, context_note |

`display_group` (mammal, bird, reptile, amphibian, fish, insect, arachnid, mollusc, crustacean, coral, other_invertebrate) lives on the revision. That keeps the rule that everything public is revisioned.

### Reference and shared
| Table | Fields |
|---|---|
| sources | title, publisher, authors, url, doi, published_on, accessed_on, license, permitted_use_note. Edits to a source cited by a published revision create a new source row; they never change the old one. |
| regions | slug, name, type (`country`/`ocean`/`sea`/`other`), iso_a2, parent_id, geom (simplified for display), source_id |
| habitats, threats | code, name, parent_id. Seeded from the IUCN Habitats and Threats classification schemes if their licence allows; otherwise from a documented in-house list. |
| media_assets | storage_key, mime, width, height, bytes, creator, credit, license (allow-list), source_url, review_state |
| organizations | name, slug, website, description, review_status, reviewed_at, reviewer_id |
| support_links | organization_id, url, action_type, description, last_checked_at, last_status, editorial_status |
| staff_users | email, name, password_hash (argon2id), role (`editor`/`admin`), disabled_at |
| staff_sessions | user_id, token_hash, created_at, expires_at, revoked_at, ip_hash, user_agent |
| staff_tokens | user_id, token_hash, purpose (`invite`/`reset`), expires_at, consumed_at |
| audit_events | actor_id, action, entity_type, entity_id, summary (redacted), created_at. Append-only, enforced by a DB trigger or revoked UPDATE/DELETE grants. |

### Editorial JSONB
Validated with a versioned zod schema (`schema_version`). Holds: overview, taxonomy lineage for display, diet narrative and tags, climate narrative, optional measurements with units, biology, conservation-action text. Every section key maps to `revision_citations`. Migrations for older schema versions live in code and are covered by tests. Diet and climate tags move to tables only when a real filter needs them (documented path in `DATABASE.md`).

### Constraints (in the database, not only in code)
- Populations are nonnegative, `min ≤ max`, and the form matches the populated columns (CHECK). Reference start ≤ end.
- Regional scope requires `region_id`. Global scope forbids it.
- `species.published_revision_id` must point to a revision of the same species (composite FK on `(id, species_id)`).
- An estimate's `assessment_id` must share the estimate's revision (composite FK).
- Unique slugs, provider IDs, per-species versions and join rows.
- Geometry: `ST_IsValid`, SRID 4326, a vertex-count limit, antimeridian-safe storage (split at ±180).
- bigint values are serialized as strings in JSON.
- GiST indexes on geometry. GIN on the search tsvector. B-tree on every filter join. Representative query plans go in `DATABASE.md`.

### Publication
- Editing copies the published aggregate into a new draft.
- Publish validates the revision, then in **one transaction** marks it published and switches `published_revision_id`, writes an audit event, and then triggers revalidation.
- Every public query joins through `published_revision_id`. There is no other path to child rows (enforce this with a single repository method plus a test).
- Rollback moves the pointer back to an earlier *published* revision.
- Optimistic concurrency: a draft carries `base_revision_id`, and publishing fails if the species' current published revision has changed since then.
- Scientific history is deduplicated by `provider_assessment_id` across published revisions. Abandoned drafts are excluded.
- A support link may be disabled immediately, which is audited and does not create a new revision. Re-enabling it requires review.

## 7. Editorial workflow

**Roles:**
- **Editor:** creates, edits and submits drafts.
- **Admin:** does everything an editor can, plus reviews, publishes, rolls back, archives, and manages staff, media review and the support directory.

A solo admin may self-publish. The UI then records "self-reviewed" and never claims independent review.

**States:** `draft → submitted → published`. `submitted → changes_requested`, after which the editor continues in a new draft revision. Published and submitted revisions are immutable.

**Staff accounts in R1:** the first admin is created by a CLI command (`npm run admin:create`) driven by environment variables. Admins invite staff by generating a one-time link that is shown once in the UI. R1 sends no email. A local mail sink (Mailpit) is used only if email is added later.

**Editor UI:** the editor mirrors the public profile's sections. It includes a source picker that can create a new source, live preview using the public components, a changed-fields diff against the published revision, and a publication checklist.

**Publication checklist (blocking):**
- Accepted scientific name and at least one provider identifier.
- An overview with at least one citation.
- A status or an explicit "Not assessed".
- A population section with estimates or an explicit "Unknown".
- Every numeric claim cited.
- Every image is `review_state = approved` with a licence on the allow-list, or the profile shows the neutral no-photo state.
- Every geography row has a source.
- Reviewer attribution recorded.

Missing ecology (diet, climate) does not block publication. It is shown as "Not yet documented".

**Development fixtures** (synthetic taxa named clearly, e.g. *Fictus exemplaris*): unknown population, a regional assessment, a wild/captive split, breeding pairs, multiple estimates, a marine species, an antimeridian range, a sensitive generalized species. Fixtures never appear in a production seed.

## 8. Data sources and licensing

**Feasibility first (M0).** Before any integration, fill in `docs/DATA_SOURCES.md` with one row per field. Columns: desired field, provider, identifier, coverage, access method, licence, display/storage/redistribution permission, required attribution, refresh policy, status (`approved`/`pending`/`unavailable`). Every licence claim links to the provider's current terms page. Having API access does not mean having redistribution rights.

**Likely sources (each must be verified, nothing is assumed):**
- **IUCN Red List:** status, trend, habitats, threats, population text. Its terms restrict reuse and redistribution. Until terms are confirmed for this use, staff summarize manually with citation and a link to the assessment, and no bulk import is built.
- **GBIF:** taxon keys and names. Occurrence data is for discovery only. It is never a population figure and never a range boundary.
- **Images:** Wikimedia Commons and iNaturalist per-file licences. **Allow-list:** CC0, Public Domain Mark, CC BY, CC BY-SA. NC-licensed images are excluded by default because R3 may involve fundraising. Record creator, licence, source URL and any modification.
- **Diet and climate:** specialist literature or handbooks, synthesized by editors and cited.

No scraping sites whose terms forbid it. Rendering a published profile never depends on a live third-party call.

**R1 import CLI:** `npm run import -- <file> --dry-run | --apply`. JSON/CSV is validated with zod. It matches on stable provider IDs, creates drafts only (never publishes), applies each file in one transaction, writes a Markdown change report, and is idempotent: re-running the same file produces no changes. Manually edited fields are never overwritten without `--reconcile`, and every overwrite is listed in the report.

**Link checker:** `npm run links:check` records the HTTP status of every support link and flags failures for review. It never auto-disables a link.

**Review cadence** is a product policy, not a claim that the data is live. Example: high-interest profiles and support links are reviewed quarterly.

## 9. API and security

**Public endpoints (published data only):**
```
GET /api/v1/species?q&group&environment&category&region&habitat&trend&sort&page&pageSize(≤48)
GET /api/v1/species/:slug
GET /api/v1/filters
GET /api/v1/regions/:slug
GET /api/v1/map?bbox&group&category        (bbox validated, antimeridian-aware, result & vertex caps)
GET /api/v1/compare?species=a,b,c          (max 3, 400 otherwise)
GET /api/v1/support
```
Pagination, filters, limits and a single error shape (`{ error: { code, message, details? } }`) are documented in OpenAPI. Responses are purpose-built DTOs. Raw users, sessions or drafts are never serialized.

**Staff endpoints** cover auth, drafts, submit, review, publish, rollback, media, sources, organizations, support links and staff. Authorization runs in a backend guard on every mutation and is covered by tests.

**Auth and sessions:**
- Passwords: argon2id, minimum 12 characters, checked against a breached-password list if one is available offline.
- Sessions: an opaque random token stored hashed. The cookie is `__Host-`, HttpOnly, Secure, SameSite=Lax. 12-hour idle timeout and 7-day absolute limit, revocable.
- CSRF: double-submit token plus an Origin check on every mutation.
- Rate limits on login and token endpoints, plus lockout with backoff.
- No SMS. No secrets in localStorage, git or logs. No default production password.

**Uploads:**
- Size limit, magic-byte type check, and an allow-list of JPEG, PNG and WebP. No SVG or HTML.
- Images are re-encoded, which also strips metadata.
- Staff-entered source or media URLs are fetched only through an SSRF-safe fetcher: https only, private and loopback IPs blocked after DNS resolution, size and time limits, no redirects to blocked hosts.

**External links:** support links are rendered directly with `rel="noopener noreferrer"`. There is no open redirect endpoint. Click tracking, if enabled, is a fire-and-forget beacon.

**Headers:** CSP (including the map tile/style origins), HSTS in production, `X-Content-Type-Options`, `Referrer-Policy`, and `frame-ancestors 'none'`.

## 10. Conservation support

**R1:** reviewed external action links only. Each link shows the organization and the destination domain. A click counts as a referral, not a donation. No funds-raised figures and no leaderboards. The organization review criteria are published on `/support`, and site review does not certify how effective an organization is.

**R3 (not now):** campaigns, organization members, donations and payment events. Money is stored in integer minor units with currency exponents. Webhooks are verified, events are idempotent and state transitions are atomic. Refunds and disputes are handled. Donors are private by default. Live payments need the operator, provider, jurisdiction and payout arrangement settled first, and nothing assumes Stripe is available. Never claim tax deductibility.

## 11. Success measures

**R1 is done when** a visitor can find a species, understand its population estimate, see where it lives, compare it with another species and open a credible support link. If 3–5 testers are available, run these tasks with them. User-research results are never fabricated.

**Analytics (optional, privacy-conscious, aggregate only):** searches, zero-result searches, profile views, compare use, map errors, support clicks. No emails, coordinates or raw free-text search terms. Use a self-hostable cookieless tool or none at all.

**Quality reports (`npm run validate:catalogue`):** 100% of published numeric claims cited, 100% of published images licensed and approved, zero drafts reachable publicly, zero mixed units in compare.

**Performance:** measure, never invent. Layouts must work at 360px with no horizontal overflow. Profiles are server-rendered. Paginated API p95 is reported along with test conditions. The map loads after the list and does not block it.

## 13. Testing, operations, documentation

**Tests that must exist** (risk-based, not cosmetic):
- Null vs zero vs unknown population.
- Unit and basis separation in compare.
- Revision consistency across catalogue, map, compare and profile.
- Draft leakage.
- Authorization on every staff route.
- CSRF.
- Concurrent publish conflict.
- bbox validation and antimeridian handling.
- Geometry limits.
- Sensitive geometry.
- Import idempotency and `--reconcile`.
- Credit and licence snapshot retention.
- SSRF and upload rejection.
- Editorial JSONB schema migration.

**CI:** install, typecheck, lint, contracts drift check, unit tests, integration tests against PostGIS, build, then the Playwright critical suite.

**Operations:**
- Schema changes go through migrations only; never `drizzle-kit push` outside local development.
- The DB is not exposed publicly, and secrets come from the environment.
- Backups cover PostgreSQL (`pg_dump`) **and** the media bucket, stored separately from the app host. A restore runbook exists.
- Migration rollback limits are documented.
- On a shared VPS, use explicit ports and a separate compose project name, and never touch other services.

**Docs:**
- `README`
- `ARCHITECTURE`

- `DATA_SOURCES`
